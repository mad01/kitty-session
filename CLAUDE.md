# CLAUDE.md — kitty-session

`ks` is a session manager for the [kitty](https://sw.kovidgoyal.net/kitty/) terminal. It runs a kitty instance of its own. Every session is one tab in it: the ks sidebar (a Bubble Tea agent list) on the left and the session's agent on the right. The agent is one of three kinds: `claude` (Claude Code, the default), `pi`, or `shell` (kitty's default shell, no agent at all). The tab bar is hidden; the sidebar is the tab list. It tracks each session's state and brings every session back on attach. The user's own kitty is never touched. `README.md` is the front door; the `docs/` set is the deep dive. This file is the agent-facing working context: where code lives, how the on-disk model works, and the gotchas that bite.

Go module `github.com/mad01/kitty-session`, builds to a single `ks` binary. Needs Go 1.25+.

## Where things live

```
cmd/ks/main.go              entry point — calls internal/cli
internal/cli/               cobra subcommands (attach = bare ks, new, open, close, list, rename, move, quit, sidebar, tmp, repo, import, hooks, _hook, _pi-hook, _sidebar-demo, version)
internal/sidebar/           Bubble Tea agent list, run as `ks sidebar`; every side effect behind sidebar.Backend
internal/hooks/             the ks matcher groups in ~/.claude/settings.json (install, uninstall, installed)
internal/herdr/             reader for herdr's session.json (Load, Agents, Running); `ks import` is its only caller
internal/cmux/              the ONLY place that runs the cmux CLI (new-workspace); used by `ks import --to cmux`
internal/instance/          the ks kitty instance: Ensure (ping or start), Connect, Client, Shutdown
internal/launcher/          Launcher: Open/Close/Rename/Move/Attach/Alive; tab topology behind a backend interface
internal/kitty/client.go    the ONLY place that runs `kitty`: Client (every `kitty @ --to <socket>` call) and Start
internal/session/           Session struct + Store (save/load/list/delete/rename/restore)
internal/state/file.go      state JSON read/write + freshness predicates
internal/claude/            screen classifier (ParseScreen; DetectState on top of it) + Claude projects reader (LatestPrompt)
internal/procinfo/          parent/comm lookup for the hook's nested-claude guard
internal/repo/config/       ~/.config/ks/config.yaml loader
internal/repo/finder/       concurrent BFS repo walker + remote-URL parser
pi/ks-agent-state.ts        the pi extension: runs `ks _pi-hook` on pi's lifecycle events (docs/pi.md)
```

`internal/cli` depends on almost everything. `instance` and `launcher` are the two mid-layer packages: `instance` owns the kitty process, `launcher` everything inside it, including `launcher.SidebarBackend`, the production `sidebar.Backend`. `sidebar` never imports `launcher`; `launcher` imports `sidebar` for the interface and row types. Leaf packages have a single responsibility and don't import their peers. See `docs/architecture.md` for the package graph and the create-session, attach and detect-state flows.

**`internal/kitty` is the one exec boundary.** `kitty.New(socket)` returns a `Client`; each method wraps one `kitty @` subcommand and always passes `--to <socket>`. `Client.Start` is the only call that runs the kitty binary itself (`kitty --detach --listen-on ...` plus the `-o` overrides the topology depends on). Nothing else in the tree calls `exec.Command("kitty", ...)`. If you need a new kitty interaction, add a method to `client.go`. The repo finder also avoids subprocesses: it parses `.git/config` directly, never running `git`.

**Which wiring to use in a command.** `ensureWiring` (in `internal/cli/wiring.go`) starts the instance when it is down; `new`, `open`, `tmp` and attach use it. It also reports whether it had to start it (`wiring.started`); `new`, `open` and `tmp` then call `Launcher.Resume` first, so the tabs come back in sidebar order (`sortForResume` in `attach.go`: sessions ranked by `ks move` first, the rest by creation) and their own tab comes last. `offlineWiring` never starts it; `close`, `rename`, `move` and `list` use it so they work while the instance is down (`move` then fails with the kitty error, since it needs a tab to move). Both hand back the store, the config (nil when the file is absent) and a `Launcher`.

**The agent command, per kind.** `launcher.AgentCmd(sess, mode)` builds the right-hand window's command from `sess.Kind()`. Claude is a bare `claude`, `--resume <id>` when the record's transcript still exists, `--continue` when the directory has any transcript. Pi is `pi --session <pi_session_path>` on a reopen while that file exists and a bare `pi` otherwise; never `pi --continue`, since what it does with nothing to continue is unverified. Shell is no command at all, which makes `kitty @ launch` run the default shell, the same way `SidebarBackend.ShellSplit` opens one. The kind comes in through `launcher.Request.Agent` (`ks new --agent`, `ks tmp --agent`, the sidebar's kind step) and `target` writes it on the new record; a reopen uses the stored kind. Both windows of every session get `KS_EXE=<path of the running ks binary>` beside `KS_SESSION_ID` / `KS_SESSION_NAME`, so the pi extension calls the ks that made the session.

**Commands a session can run on itself.** `ks rename <new>` and `ks move <where>` with one argument act on the session the process runs in, resolved by `selfSession` in `internal/cli/self.go`: `KS_SESSION_ID` first (`store.FindByID`), `KS_SESSION_NAME` only for records that predate ids, since the name goes stale after a rename. The hook's lookup shares `findSession`.

## On-disk model

Everything `ks` writes lives under `~/.config/ks/`:

```
~/.config/ks/
├── config.yaml            user-authored (the only config; no per-repo, no env override for the path)
├── kitty.sock             the instance's remote-control socket (kitty_socket in config)
├── sessions/<name>.json   one per live session
├── sessions/trash/<name>.json   moved here by `ks close` (no --keep) and the sidebar's delete
└── state/<name>.json      written by hooks or the --agent monitor
```

A session file holds the kitty IDs (`kitty_tab_id`, `kitty_window_id` for the agent window, `kitty_sidebar_window_id`), the working dir, a created-at stamp, `status`, `agent` (`claude`, `pi` or `shell`; absent means claude, read it through `Session.Kind`), the Claude session id and transcript path from the last `SessionStart` hook, `pi_session_id` and `pi_session_path` from the last `session_start` the ks pi extension reported (pi records only), `focused_at`, `viewed_at`, and `position` (the session's rank among the open ones, 1-based; written by `ks move` and kept current by every tab launch after that; absent until a move). A tab is seen while it is on screen and the kitty window is the active one (the OS window's `is_focused` in `kitty @ ls`). `viewed_at` is stamped the moment the session's tab becomes seen or is opened from any sidebar, and once more when it stops being seen. While it stays seen its own sidebar refreshes it at most every 10 s. A state file newer than it, of any state but `waiting` (a launch is not activity), marks the row unread while the tab is not seen. The name then draws in the accent colour; the dot and the sort order are unchanged. A state-file `idle` newer than it shows as `done`, the unread case where the turn also finished. A turn that finishes in the visible tab while another app is active stays `done`, and is read when you come back. A relaunch (a new session, or a reopen of one whose window is gone) removes the old state file before the launch; the `SessionStart` hook writes a fresh one. So an attach never shows a stale `input`. Without a state file (no hooks, no screen check, no pi extension) nothing marks a row unread. **Kitty IDs restart from 1 in every instance**, so after `ks quit` a stored id can point at another session's window. The launcher therefore tags both windows of a session with the kitty user variable `KS_SESSION_ID=<id>` (`launch --var`, read back as `user_vars` in `kitty @ ls`) and only trusts an id when the tag matches. A record with no `id` owns nothing. Records from older versions may carry `kitty_shell_window_id` / `kitty_summary_window_id`; they are cleared on the next reopen.

State files are `{"state": "...", "updated_at": "..."}` where state is `working` / `idle` / `input` / `error` / `waiting`. The one freshness threshold lives in `internal/state/file.go`: `freshness = 10s`, the age under which `ks list` trusts the file outright and the sidebar honours an `input`.

## State detection: four sources, in preference order

1. **Program status** (preferred; needs a kitty that passes it). The Program Status Protocol by Mitchell Hashimoto (https://www.superlogical.com/rex/docs/build/program-status): a program writes an Operating System Command (OSC) sequence, `OSC 7501 ; state=working:kind=…:msg=<base64> ST`, to its terminal. Claude Code emits it since 2.1.295, pi since 1.1.0. kitty keeps the records per window and lists them under `program_status` in `kitty @ ls`, the snapshot the sidebar already polls, so ks reads them with no new kitty call and no hook. `internal/kitty` reads only each record's `state` and keeps the most urgent as `Window.Status`, a `kitty.ProgramState` (blocked > error > done > working > idle; `""` without a record). `kind`, `msg`, `id`, `progress`, `app` and `title` are ignored. Mapping (`launcher.ProgramState`): `blocked`→`input`, `working`→`working`, `done`→`done` (`idle` on a seen tab, on screen in the active kitty window, since the user is looking at it), `error`→`error`, `idle`→`idle`. Applies to every kind, since the record is the program's own word; a shell session running a 7501-aware program reports too. A fresh (<10 s) state file outranks the record (`launcher.ReportedState`): the hooks saw an event the record may not reflect yet.
2. **Claude Code hooks** (most accurate without program status; always needed). `ks hooks install` registers a hidden `ks _hook` handler for ten events in `~/.claude/settings.json`. `UserPromptSubmit`/`PreToolUse`/`PostToolUse`/`PostToolUseFailure`→`working`, except `PreToolUse`→`input` for `AskUserQuestion` and `ExitPlanMode` (both block on the user and fire no `PermissionRequest` or `Notification` under bypass-permissions mode). `PermissionRequest`→`input`, fired as the dialog is about to show; `Notification permission_prompt` is the fallback, about six seconds later. `Stop`→`idle`, `StopFailure`→`error` (API error, rate limit, auth failure), `SessionStart`→`waiting`, plus `SessionEnd` for the stopped status. An `input` entry records the tool that asked in `tool`, and `PostToolUse`/`PostToolUseFailure` replace it with `working` only for that tool (an `input` from `Notification` has no tool and any completion clears it). Events carrying an `agent_id` (an in-process subagent) write only `input`, stamped with the subagent's id and the tool; that subagent's own `PostToolUse`/`PostToolUseFailure` for the same tool clears it. Every other subagent event writes nothing, so a background subagent cannot overwrite the parent's `input` or `error` or idle the parent when it finishes. Every handler carries `"timeout": 5`, since `PermissionRequest` is synchronous in Claude's permission flow and the default is 600 s. Install and uninstall keep every field of other tools' entries, `timeout` and `async` included. An event whose value is not an array is left alone by uninstall; install refuses to add a ks group to it with an error naming the event. Claude Code fires no hook on Escape or a manual deny, and `Stop` does not run on an interrupt. As far as the hooks go, a dismissed prompt's `input` lasts until the next event they see (the next message, a `/clear`, an exit). When kitty passes no program status, the screen check of item 4 clears it within one sidebar poll. That needs the file older than 10 s and the dialog gone. With program status the record already takes over after ten seconds. The folder-trust dialog and a login prompt at startup (no hook has run yet), and every dialog while the hooks are not installed, show as `input` the same way. The handler keys off `KS_SESSION_ID` / `KS_SESSION_NAME`, which the launcher exports into both windows of a session. Unset env → handler exits silently, so the hook is safe to leave installed globally. Program status does not replace them: `SessionStart` is where the resume id and transcript come from, `SessionEnd` where `stopped` does, and the state file is the badge's source on a kitty without 7501.
3. **Background Haiku agent** (optional fallback). `ks sidebar --agent` runs a long-running `claude` with a tight allow-list that polls `kitty @ --to <socket> get-text` every 5s and writes state files; `ks --agent` passes the flag to the home sidebar when it starts the instance. Killed with its process group when that sidebar exits.
4. **Title glyph / screen text** (always-on). The sidebar reads the claude window's title from the `ls` snapshot it already has: `internal/claude.ParseTitle` maps Claude's leading spinner glyph to `working` and `✳` to `idle`. The screen classifier `internal/claude.ParseScreen` (`internal/claude/screen.go`) reads the bottom of the window's text (`get-text --extent all`, cut to the window's own row count) and reports three flags. The dialog rules look at the last 24 non-empty lines, the running-turn rules at the last 12. A dialog is on screen (blocker). The prompt box is at rest (a `❯` line between the last two horizontal rules with no dialog footer in the box). A turn is running (an `esc to interrupt` line, or a spinner-glyph line ending in `…`). The blocker rules come from herdr's Claude manifest (Apache 2.0) plus a ks rule for the folder-trust dialog. Any of these matches: `esc to cancel` with `enter to confirm`, or `enter to select` plus an arrow-key hint (the words, or `↑/↓`); `do you want to proceed?` with a numbered `❯ 1. Yes` style option line; `MCP server "…" requests your input` with Accept/Decline and `esc to cancel`; `review your answers` (AskUserQuestion review); `skip interview and plan immediately` (plan interview); `waiting for permission`; `do you want to allow this connection?`; `trust the files` with `enter to confirm`. The transcript viewer and the model picker report nothing, so they never change a state. `ks list`'s `DetectState` maps the flags: dialog → `input`, running → `working`, prompt box → `idle`, welcome screen → `waiting`, anything else `waiting`. The sidebar's screen check (the backstop) runs in the session's own sidebar only, for its own row, after `resolveState`, and never when the window carries a 7501 record. Two cases. (1) The clear, on every 3 s poll: the row is `input` and the state file is older than 10 s. A dialog on screen keeps `input`, whatever else shows. Otherwise a running turn rewrites the file to `working`, and the prompt box at rest rewrites it to `idle`. The row then reads `idle`, or `done` while the tab is not on screen or the kitty window is not the active one, since the file's `idle` is newer than `viewed_at`. An unreadable window leaves it. (2) The raise, reading at most once every 10 s: the row has no state file, or a stale `waiting`, which is a dialog at startup. The folder-trust dialog comes before any hook runs; a login prompt reports nothing. While the hooks are not installed any dialog at any time qualifies, which is what makes ks usable without `ks hooks install`. A visible dialog writes `input`. Before writing, the sidebar re-reads the state file and skips the correction when a hook wrote in the meantime. Because the session's own sidebar writes the shared state file, every other sidebar and `ks list` follow without reading the screen. `error` is never touched. A Claude UI change no rule matches fails safe: the row keeps today's behaviour. Text matching by design; loses to UI changes.

Before any of that, both ask `Launcher.Alive` (or `findLive` on the shared snapshot): a `stopped` record, or no tagged window matching `kitty_window_id`, is `stopped` without reading anything. The sidebar's full rule set is `resolveState` in `internal/launcher/sidebar_backend.go` (table-tested). Right after the stopped check, for every kind: a fresh state file hands over to the kind's own rules below; otherwise a record, when kitty lists one, decides (`launcher.ReportedState`, shared with `ks list`); otherwise the kind's own rules. For claude: fresh (<10 s) state-file `input`, `error` then `working` win first, then a working title glyph, then a state-file `input` or `error` of any age (sticky: only a later hook or the working glyph clears it), then the `✳` idle title (which becomes `done` when the state file's `idle` is newer than the record's `viewed_at`), then a state-file fallback. A fresh `working` file outranks `✳` because `✳` doubles as a spinner frame. After `resolveState` the session's own sidebar runs the screen check of item 4 on its own row, which rewrites the state file so the row and every other reader follow. For pi there is no title glyph, so the state file alone decides, whatever its age: `input`, `working`, `idle` newer than `viewed_at` is `done`, anything else `idle`. The ks pi extension writes that file through the hidden `ks _pi-hook`; its `session_shutdown` never marks the record stopped, because pi reports `quit` for the SIGHUP of `ks quit` too (`docs/pi.md`). A shell is `idle` whenever its window is there; nothing else reports its state. The sidebar's `error` state (the agent reported a failure and stopped) ranks between `input` and `done` and draws as a steady `✗` in the error colour. It comes from a 7501 record or from the `error` the `StopFailure` hook writes to the state file. The `waiting …` age on an `input` row still comes from the state file (the hooks write `input` for the same prompt), so without hooks it reads zero. `ks list` follows the same order through `launcher.ReportedState` (a record prints `input`, `working`, `done`, `error` or `idle`), then its own per-kind rules: a fresh state file or the screen classifier for claude records, a pi record's state file, `idle` for a shell record. A stale `error` file still prints `error` unless the classifier finds Claude working. Full event tables and the classifier rules: `docs/hooks-and-state.md`; the sidebar's rules: `docs/tui.md`.

**Notifications ride on the resolved state.** Each session's own sidebar, and only it, posts a desktop notification for its own row through kitty's desktop notification protocol (OSC 99, https://sw.kovidgoyal.net/kitty/desktop-notifications/), written to its own terminal. The sidebar sits in the session's tab, and the request carries `o=invisible`. So kitty shows the banner only while that tab is off screen or the kitty window is not the active one. A click on the banner focuses the sidebar window, which brings the tab to the front. The `notify` list in `config.yaml` picks the transitions: default `[input]`, `[input, done]` adds turn completions, `[]` turns them off, anything else is a config error naming the value. Entering `input` posts `<name> needs input` (body: the row's title or directory, sound `question`) and leaving it withdraws the banner; `done` does the same with `<name> finished` and sound `info`. A sidebar that starts while its session already waits posts at once; a relaunch removes the old state file first, so an attach never posts for a stale `input`. A banner is withdrawn when the row leaves the state, on close or delete from the sidebar, and when the sidebar reaps its tab after claude exits. `ks close` from a shell and `ks quit` leave the banner until dismissed, and a click on it then does nothing. The home sidebar posts nothing. No delay (kitty's visibility gate is the suppression; a prompt answered within one poll just has its banner withdrawn), no per-session opt-out, no `error` banner. Because the banner is computed from `resolveState`'s result, whatever source produced `input` (hook, 7501 record, screen check) produces the banner too. `ks _sidebar-demo` turns notifications on for its demo row, so in kitty it previews the banners. Only kitty implements OSC 99 here; other terminals ignore the sequence.

Tests live next to the code. The heavier ones set `HOME` to a `t.TempDir()` so the session/state/config code reads from the tempdir; a few shell out to real `git init` / `git remote add` to exercise finder logic. Nothing drives kitty: `internal/kitty` tests inject a runner and assert the argument list, `internal/launcher` tests run against the in-memory instance in `fake_test.go` (window table, call sequence), `internal/instance` against a scripted pinger. `internal/cli/repo_test.go` is the pattern for capturing cobra output against a fake `HOME`.

Live check by hand, with the branch build and never `make install`: `./ks new -n smoke -d /tmp/smoke`. Then `kitty @ --to unix:$HOME/.config/ks/kitty.sock ls` should show just a `smoke` tab (the home tab closes once a session tab exists and comes back when the last one closes), with the sidebar at `sidebar_width` columns and claude beside it. `get-text --match id:<sidebar window>` should print the framed list: an `agents … tab order` header, a `smoke` row, a `new … menu` footer. `send-text` `m` to that window opens the menu, `\x1b` closes it. `./ks quit` ends the instance. Claude's folder-trust dialog defaults to "No, exit"; send a down arrow (`\x1b[B`) before `\r` to accept. `ks _sidebar-demo` previews the sidebar on fake data without kitty. Running it from inside an agent session is fine: the instance's environment is scrubbed. Check that `ls` shows no Claude session-marker keys (`CLAUDECODE`, `CLAUDE_CODE_*`) in the claude window's `env`, and that `kitty @ ... action neighboring_window left` from the claude window lands on the sidebar.

**Adding a subcommand:** add `internal/cli/<name>.go` with a `var <name>Cmd` and an `init()` that calls `rootCmd.AddCommand(...)`. Put non-trivial logic in a new `internal/` package. Reach the instance through `ensureWiring` / `offlineWiring`, and session/state through `session.NewStore()` and `internal/state`, never the files directly. Add a test.

## Runtime prerequisites

- **kitty on the PATH.** `ks` starts its own instance with `-o allow_remote_control=yes` on the socket from `kitty_socket`; the user's `kitty.conf` needs no remote-control settings and `KITTY_LISTEN_ON` is irrelevant, since every call passes `--to`. The instance still reads `kitty.conf` for appearance. Verify with `kitty @ --to unix:$HOME/.config/ks/kitty.sock ls` while an instance runs. Tested with kitty 0.48.2.
- **`claude` on the caller's PATH.** Every launch path forwards `PATH` into both windows via `--env`, so a `claude` under `~/.local/bin` is found even though `kitty @ launch` runs with the instance's environment.

## Repo finder

`ks repo` (and the sidebar's `n` picker, through `SidebarBackend.Repos`) walk the `dirs` from `config.yaml` with a 32-worker concurrent BFS, stopping at the first `.git` in any subtree, deduped by absolute path. Names come from parsing the `origin` URL in `.git/config` (SSH and HTTPS; last two path components for deep GitLab subgroups); no `origin` → fallback name `<parent>/<dir>` with empty host. Output modes: interactive fuzzy finder (default), `--list` (TSV), `--json`, `--toon` (token-efficient, for LLM consumers). The MCP/search/zoekt stack that once lived here now lives in [`csl`](https://github.com/mad01/code-search-local); `ks` kept `repo` only so the shell `repo()` helper keeps working.

## Dotfiles wiring & catalog

Installed via the dotfiles `kitty-session` recipe (`recipes/kitty-session/` — clones this repo, `make`-builds, installs `~/code/bin/ks`, symlinks `config.yaml`, registers the `ct` shell function = `ks tmp`). Ensure `~/code/bin` is on `$PATH`. Uninstalling the recipe wipes `~/.config/ks/sessions/`.

Catalogued via root `service-info.yaml`: System `kitty-session`, Component `ks`. Update it if the tool's shape changes; run `catalog validate .` before committing (names are globally unique across the catalog).

## Gotchas

- **Kitty IDs are per instance.** Never decide liveness or close a tab from a stored id alone; go through `Launcher.Alive` / the tagged-window snapshot (`findLive` in `internal/launcher/topology.go`).
- **The instance inherits the environment of whoever starts it.** `kitty.Start` drops the Claude Code session markers (`claudeMarkers` in `client.go`) and every `KS_*` / `KITTY_*` except `KITTY_CONFIG_DIRECTORY`, and every launch unsets those same markers in the child (`unsetInWindows`). It does NOT drop all `CLAUDE*`: `CLAUDE_CONFIG_DIR`, the Bedrock/Vertex flags and auth tokens must survive. Without the marker scrub, a ks run from inside a Claude Code session made every claude it hosted a child session with transcript saving off. `PATH` is forwarded per window.
- **A new tab opens in the `fat` layout**, which ignores `--location=vsplit`; the topology switches it to `splits` first. Split sizes are fractions, so the sidebar is pinned by measuring `columns` and resizing, up to two passes.
- **Session tabs are built hidden.** Both launches pass `--keep-focus`, so a tab appears only once its split and width pin have settled, through the one `focus-window` in `Open` (skipped for `Request.Background`, which Attach uses for every resume before it focuses one session). From the sidebar, `--location=vsplit` already puts claude on the right. Never add a `layout_action` to the topology: `kitty @ action --match … layout_action` acts on the active window of the *visible* tab whatever `--match` names (probed 2026-10-05: an action aimed at a hidden tab moved the visible tab's window).
- **Never pass `--title` to the claude window.** Claude's own OSC title is the sidebar's state signal and its row title.
- **`kitty @ get-text` honours the scroll position.** With the default extent it returns what the viewport shows. Once the user has scrolled up that is a slice of the scrollback, not the live screen (probed on kitty 0.48.2, 2026-10-16). `ks list` and the sidebar's screen check pass `--extent all`, which always ends at the live bottom, then keep only the window's own row count (the `lines` field of `kitty @ ls`). Without that cut, rows left in the scrollback above a short screen (after `/clear`) can pose as a running turn or a dialog. `internal/kitty` has only that reader; the viewport one is gone.
- **Tabs can only be reordered through the active tab.** `kitty @ action --match … move_tab_forward|move_tab_backward` ignores `--match` and moves the tab that is showing (same trap as `layout_action`), and `detach-tab --target-tab` makes a new tab at the end instead of reordering (probed 2026-10-06, kitty 0.48.2). So `Launcher.Move` focuses the session's tab, steps `MoveActiveTab`, then focuses the window that had the keyboard; a tab moved from behind another is on screen for a moment. After the move it renumbers `position` on every open session from a fresh snapshot, and once any session is ranked every tab launch in `Open` does the same (`rerank`), so a reopened or new session takes the bottom rank and the stored ranks never disagree with kitty's order. A store that never saw a move stays unranked.
- **`--next-to` is ignored unless `--match` selects its tab.** `LaunchHSplit` passes both (`--match=id:<claude> --next-to=id:<claude>`); with `--next-to` alone kitty splits the active tab's active window instead. `LaunchVSplit` gets away with `--match` only because the sidebar is the tab's sole window at that point.
- **ks maps no keys in the instance.** Moving between the sidebar and claude is the user's own kitty window keys (`cmd+]` / `cmd+[` in the dotfiles config) plus `l`/`tab`/`q`/`enter` from the sidebar. `ctrl+b` and `ctrl+w` reach Claude (background a task, delete a word). Chords are opt-in: `kitty_overrides` entries like `map ctrl+b>s neighboring_window left` go to kitty as `-o`, which accepts `map` lines.
- **The home tab is the tab whose sidebar carries `KS_HOME`, and it exists only while no session tab does.** A session-less `ks sidebar` sets that tag on its own window at startup (`kitty.Start` cannot pass `--var` to the instance's first window, so the sidebar tags itself; `ks sidebar --agent` adds `KS_HOME_AGENT`), and `openHome` passes it as `--var`. `instance.Ensure` also tags the first window itself right after a start it made, before it returns: the sidebar's self-tag and the starting command's first `Open` both poll the socket at the same cadence, and an `Open` that won would leave the home tab untagged behind the first session tab. `Open` retires every tagged home tab (`retireHome` in `topology.go`) once a session tab exists, except one carrying `KS_HOME_AGENT`; `closeTabs` recreates it (`openHome`) only when closing the session's tab would leave the instance with no tab at all, because the instance quits with its last window. A tab with neither `KS_HOME` nor `KS_SESSION_ID` is the user's own (cmd+t): ks never closes, counts or recreates it, and it holds the instance up by itself (MAD-383). The home tab of an instance started by an older ks is untagged, so it counts as a user tab and lingers until `ks quit` or the user closes it; there is no migration. Never identify the home tab by id.
- **The sidebar never exits on its own, but a session's sidebar closes its own tab once its claude is gone.** `ctrl+c` is swallowed; the exits are the menu's `quit ks` (instance.Shutdown), the instance going away, and the sidebar's own tab closing under it. On every `List` tick the session sidebar checks its claude window in the snapshot it already holds (`reapIfGone` in `internal/launcher/reap.go`). Seen once and then gone (`/exit`, crash, kill), or never seen within `reapGrace` (30 s) of the first tick, it closes its tab through `closeTabs`, so the home tab is recreated first when it was the last one. Any other window tagged with the session holds the tab open until it goes too (a shell split, or a claude relaunched beside the sidebar before the record carries its id). A close kitty refuses is not retried. The record and the state file are untouched: the SessionEnd hook already marked an explicit `/exit` stopped, and a crash leaves the record `active` so the next `ks` resumes it. The home sidebar never reaps, and nothing reaps on a failed snapshot. Run by hand with no instance it exits at once with `ks instance not running`. Inside the instance it waits for the socket (`instance.Await`, keyed on `KITTY_LISTEN_ON`), since kitty starts the home sidebar before the socket necessarily answers.
- **Sidebar frames are written inside synchronized-output markers** (DEC mode 2026, `syncOutput` in `internal/sidebar/output.go`). Recolouring the frame rewrites every line, and the macOS pty feeds kitty large writes in small chunks; the markers make kitty paint the whole frame at once instead of flickering through partial ones. Terminals without the mode ignore the markers.
- **`ks quit` ends every session's claude** (SIGHUP). Records stay `active` and come back on the next `ks`. A reopen uses `--resume <id>` with the record's own transcript, `--continue` when the directory has any transcript, and a bare `claude` otherwise. A session that never got a message comes back as a fresh conversation. Attach re-checks launched windows after two seconds and prints `ks: <name> exited right after launch` for any that vanished. The sidebar's reap cannot race a quit into a new home tab: `close-window --match=all` takes every window in one kitty command, the sidebars die with their windows, and a tick still in flight gets an error or a snapshot with no tab of its session, which closes nothing.
- **Program status needs a kitty that answers the probe.** Claude Code and pi send `OSC 7501 ; ? ST` at startup and wait about two seconds for the reply; with none they stay silent for the whole run. kitty answers it in master as of 2026-10-13 (kovidgoyal/kitty#10638); 0.49.2 and older do not, so there `kitty @ ls` has no `program_status` key at all (0.48.2 verified; a new kitty lists an empty one for a silent program), `Window.Status` is `""` and every row falls back to the hooks and the glyph. A claude started under an old kitty stays silent until it restarts. Lifetime rules kitty applies that matter here: `done` and `error` records drop on the next focus-in or keypress in the window, not on focus-out. So `done` on a seen tab (on screen in the active kitty window) is read as `idle`, and a result seen without a keypress reads `done` again once you switch away, until the next visit. `working`, `blocked` and `idle` drop at a new shell prompt (the OSC 133 prompt mark, so only in a window running a shell with integration; a claude or pi window has no prompt and keeps its last record until the program replaces it) and on a full reset. A window's records vanish with the window. ks never writes or clears a record.
- **Claude posts its own banner for a waiting prompt, so ks mutes it.** Claude Code sends a desktop notification through kitty when a permission prompt waits and you seem away (`preferredNotifChannel: auto`). Whenever `input` is in `notify` (the default), ks starts claude with `--settings '{"preferredNotifChannel":"notifications_disabled"}'`. The installed claude (2.1.301) documents `--settings <file-or-json>` as a JSON string to load additional settings from, and command-line settings outrank user settings. Without `input` in the list (`[]` or `[done]`) Claude's channel is left alone by design, since it is then the only signal for a waiting prompt. The live check confirms the end-to-end effect; the fallback is a `filter_notification` kitty override in `kitty_overrides`.
- **`layout` and `summary` in `config.yaml` are inert.** They still parse so old files load.
- **The `--agent` monitor costs real Haiku calls.** Leave it off unless hooks are not installed.
